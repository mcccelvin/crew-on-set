# Player profile, achievements and statistics

The main-menu Account screen and the in-game Profile HUD button (**I**) open the same profile view. It uses the original curtain/stage backdrop, girl character preview, paper panels, title signs and three icon tabs: **Profile**, **Stats** and **Shop**. Achievements open from the Stats footer and return to Stats without closing the profile. Back/Close return to the originating menu or gameplay using the existing input-state handling. All pages share the screen-scaling canvas (1920×1080 reference, Expand). Stats and achievements use clean sans-serif text, opaque paper cards and visible scrollbars. The live portrait uses the bundled stage idle and a periodic greeting, corrects imported rig/skin scaling, and uses scale-independent lighting so the mesh is neither clipped nor a black silhouette.

## Shared account details and shop

Guests use a separate device-local outfit and the current bundled catalog, refreshed on every account bind so old cached labels/artwork cannot point to another rig. Fresh guests and new website accounts start with an empty preview. Equip Boy or Girl first, then select individual free/owned items; owning an item does not automatically equip it. Existing saved outfits are retained. The Unity base FBX supplies only the skeleton: its default clothing, hair and face are hidden. Free items can be equipped; paid items can be tried on after choosing a body, with SIGN IN replacing guest purchase/top-up actions. Guest completed-level rewards persist as pending claims and are shown separately from spendable currency. Existing guest-career linking moves those claims to the signed-in account for server verification and deduplication. Guest appearance never replaces cloud account appearance; logging out restores the device's guest look.

`AccountAvatarPortrait` renders the equipped account outfit in both the main-menu `account` button (attached by `AccountProfileMenuHost`) and the gameplay Profile HUD (attached by `CareerManager`). It subscribes to `CCoinService.Changed`, so downloaded outfits and confirmed equipment changes update both entry points.

Cosmetic model keys are literal FBX filenames: `character_shirt5` uses `fbx/shirt5.fbx` in both the Unity catalog/baked rig and the website model folder. Product names, prices and website IDs are mapped once in `CharacterCosmetics`; never apply that permutation again to `CharacterCosmetics.asset`. Rebuild the derived rig with `Crew-On-Set/Cosmetics/Rebuild profile clothing rig` after source-model changes. An empty accessory slot hides the base FBX's glasses.

The Profile tab presents a compact crew identity card: copper production header, dark sans-serif labels, a read-only website username, an editable Bio field for signed-in players, and a separate account box containing the read-only ID and the existing sign-in/logout action. Guest profiles cannot edit or save name or Bio. A reusable opaque paper layer masks the original form's baked labels and oversized brown fields without changing its illustrated sidebar, border or source artwork; Stats and Shop do not receive the identity layer.

Profile paper content uses dark, unoutlined Liberation Sans text with bold headings, darker secondary notes and visible input carets. Colored buttons and the C-Coin HUD retain bold white lettering with a thin dark outline. The shared Shop uses the game's cream paper and warm brown palette with dark unoutlined text, green profile prices and the original blue-button artwork for BUY/EQUIP. This profile-only styling is reapplied when built/refreshed. The bottom account/progress status strip and its paper background are hidden on every tab, including older authored copies. The bottom SYNC ACCOUNT button is no longer created, and older copies are hidden; automatic save/wallet services remain active. Separate coin-shop popups and feedback-report typography keep their own styling.

The profile uses `ProfileCharacterPreview` instead of a frozen portrait: the original rig idles for one second after opening, plays the authored `Assets/Player/Animations/Waving Gesture.fbx`, then rests for five seconds after the full clip ends before repeating. `Resources/ProfileWave.controller` references the original humanoid clip and includes it in builds; no procedural arm rotations are applied. The preview sits on the authored platform and uses unscaled time while gameplay is paused. A playable mixer eases between idle and the gesture. Manual animation evaluation and reusable baked display meshes keep the final greeting pose visible in the portrait camera; rendering is capped at 30 updates/second. Closing/replacing the portrait releases its graph, meshes and isolated rig. TRY ON still uses the same fitted clothing and never grants ownership. The top-left C-Coin counter uses a gold C emblem, translucent gray balance bar and white numerals inspired by the B-Coin HUD; cached/pending status remains separate from the spendable balance.

`AccountProfileData` reads the website's `profile_metadata` PlayFab key, so website username and Bio changes flow into the game. Signed-in players can save Bio changes back to that same key. Changing the username opens a current-password confirmation; the game verifies the active account password, then updates PlayFab's title display name and the website username metadata while preserving the other metadata fields. Guest profiles cannot edit either field. Local drafts are kept per account, and a late reply from an old account or an earlier read cannot overwrite a newer edit. Account switching discards the previous account's draft. No live backend deployment or payment changes are introduced here.

`AccountProfileMenuHost` intercepts the existing Account scene/main-menu Account Profile entry, disabling its old display canvas while the shared view is open. It does not require changing existing menu button events. The career badge and SWITCH CAREER control are removed. Main-menu and in-game Stats use the same read-only projection of the current account's saved productions, including unsaved progress from its active career. Opening the profile does not select another career, change gameplay preferences or award currency.

Automatic login/checkpoint sync downloads/merges account-owned checkpoints and uploads pending revisions through the existing private PlayFab transport. The payload carries career stats/achievements, analytics and `PlayerMoney`; no separate or fabricated stat values are uploaded. Name/Bio refresh and C-Coin wallet refresh are separate requests. Successful checkpoint status explicitly says **Stats and B-Coin budgets synced with PlayFab**; it does not claim that C-Coins have synced. Guest/offline data remains local; stale replies are checked against the authenticated account/session. No manual profile SYNC ACCOUNT control is needed.

`AccountAppearanceData` automatically saves the confirmed equipped look to private PlayFab User Data under `character_appearance`. Its version-1 JSON contains `player_id`, `base_character` (`DefaultCharacGirlRig`), `selected_frame`, `equipped_parts` (one bundled item ID per category) and a `change_id` for read-back acknowledgement. Global per-account `SaveSystem.Appearance.v1.<accountId>` preferences retain offline edits independently of career/budget rollback. Existing cached equipped selections migrate on login; a clean device downloads the cloud choice, while a pending local edit wins until its upload is verified. DEFAULT LOOK explicitly syncs an empty selection. Login, equipment changes, periodic retry and returning focus drive sync automatically. Corrupt/unsupported/wrong-owner cloud data is not overwritten, and late replies cannot restore an older outfit or affect another account.

Appearance preferences do not grant paid ownership or change coins. `CCoinService` applies only selected items present in its matching account wallet/catalog; the separate appearance record is retained while a new device waits for its authoritative wallet. TRY ON never changes that record, and developer-wallet equipment is session-only and excluded. This stores the profile avatar's reconstruction IDs, not meshes/images, gameplay rig replication or an automatic website renderer. Name/Bio still use SAVE, and website rendering must read the new key separately.

B-Coins remain independent commercial budgets: the Stats page shows the current production's B-Coins, or the latest saved budget when no career is active, never a sum of spendable budgets. C-Coins use the account wallet; the HUD and shop show just the amount and C-COINS, without the technical "cached" qualifier. Verification stays internal, pending rewards remain separate, and server-confirmed ownership/funds still gate purchases. The `CrewCCoins` backend is **not deployed**, so this client change cannot make C-Coins authoritative or enable real purchases. Deploy and test that backend as described in `Docs/CCoins.md` before claiming live wallet sync.

The Shop uses the website's seven filters: ALL, FACE, HAIR, TOPS, BOTTOMS, SHOE WEAR and ACCESSORIES. It shows the website catalog names, categories and live C-Coin prices for mapped game cosmetics; body placeholders and portrait frames that are not website shop products are not listed. Game shop cards use the same product PNGs bundled from the website, while the original character models remain responsible for try-on and equip. The website's five free face items are automatically owned. BUY requires a connected authoritative wallet/catalog; owned parts can be equipped one per character slot. Manual SYNC/REFRESH and DEFAULT LOOK buttons are removed. TOP UP beside the balance opens `https://crew-on-set.vercel.app/portal/shop` without credentials or account data in the URL. TRY ON dresses the original `DefaultCharacGirlRig`: only the selected slot is replaced, while other clothes, hair, face and accessories remain. Successive trials can be combined; another item in the same slot replaces the previous trial. Leaving the Shop, closing/reopening the profile or a wallet refresh restores confirmed equipped items. Trials do not change ownership, wallet balance or saved equipment.

The shared Shop borrows only the supplied website reference's boxed layout, not its palette. Item cards use the game's cream paper, tan preview wells, warm brown edges/soft shadows, copper category accents, green prices and readable dark lettering. Flexible category tabs keep equal widths, 8-unit gaps and 16-unit outer margins. Balance and TOP UP share an aligned toolbar; a separate availability notice replaces repeated offline warnings on every card. Titles, prices and actions have clear hierarchy and consistent spacing. Selected categories use copper; secondary actions are outlined paper buttons. Enabled BUY/EQUIP and TOP UP use the original blue-button artwork, while disabled actions are pale with explicit UNAVAILABLE, NEED COINS or EQUIPPED states. `AlmanacProfileShop.cs` owns this presentation and the existing callback wiring. `ProfileShopGrid` lays out two cards per row within the original illustrated stage/paper frame, dropping to one column for a narrow viewport; height fitting and the existing clipped scrolling/scrollbar keep every item accessible. Cards show the matching website product artwork and catalog label alongside the existing character-model try-on preview and BUY/EQUIP actions. Category changes scroll back to the first row. No new ownership, wallet grants or payment APIs are added by this design change. Other profile tabs retain their layout.

Login, detected internet return, periodic retries and browser-focus return refresh account services automatically while the matching SDK session remains authenticated. `GameSaveManager` schedules checkpoint/result sync and requests profile, appearance and wallet refresh; `CCoinService.Update` ticks `AccountProfileData` and `AccountAppearanceData` independently of whether the profile is open. Profile name/Bio uploads retain pending local edits, busy/session guards, 45-second timeout invalidation and 60-second retry backoff. Known-offline requests are deferred, and internet reachability never counts as upload confirmation. Expired sessions still require sign-in; paid C-Coins still require the deployed authoritative backend.

`CharacterCosmeticRig.asset` contains generated skin weights and original material references for all 36 models. `CharacterCosmeticRigBaker` transfers the base body's weights in shared authored space and retains its original bind matrices, then the existing profile renderer samples the bundled idle. Hair and facial parts follow the head. Original FBXs and their import settings are unchanged. Rebuild this derived asset with **Crew-On-Set > Cosmetics > Rebuild profile clothing rig** outside Play mode after changing the models. This is a profile portrait fitting system, not gameplay/multiplayer equipment replication; new body shapes or extreme clothing may require artist-authored fit/weights. See `Docs/CCoins.md` for the catalog manifest and undeployed backend/payment requirements.

`ProfileSkillsChart` derives from `MaskableGraphic`, so the existing Stats viewport clips its polygon and grid while scrolling. It cannot draw over the heading, account subtitle or curtain background.

## Ownership and persistence

- `AlmanacProfile.cs` owns the original profile/portrait. `AlmanacProfileProgress.cs` upgrades existing authored profiles without duplicating panels, binds the Stats tab, refreshes stats and achievement cards, and preserves the existing serialized/public profile entry points. `AlmanacProfileAccount.cs` shares account inputs and the shop paper between both entry points while retiring older manual sync controls; `ProfileSkillsChart` draws the live native UI radar chart. `AccountAppearanceData.cs` owns account-scoped saved appearance preferences and their private automatic PlayFab transport; `CCoinService` still owns authoritative wallet/entitlement checks.
- `CareerProfileProgress.cs` stores fixed-size lifetime statistics in career-scoped `Profile.Career.v1` through `GameSavePrefs`. It never caches a different account/career's record. Existing checkpoint/cloud transport carries this value with the selected save; no new wallet or payment APIs are used.
- `AccountProductionProfile` reads only saves belonging to the current owner. It combines lifetime counters from independent productions, unions completed clients/observed milestones and retains graded analytics for the chart. It never activates a save. Checkpoint copies share `Profile.CareerOrigin.v1`; overlapping histories are not summed. A differing offline fork uses one whole stored lifetime record (longer tracked history first), preserves observed milestones and discloses conservative totals. Older copies use the existing reward-origin ID when available, otherwise their save ID. Deleted checkpoints can retain earned statistics but do not supply a usable budget. Completely reset or missing records are not reconstructed from invented results.
- `PlayerAnalytics.Begin` initializes tracking before a new attempt. Actual saved camera takes pass duration from `FilmCameraItem.EjectUsedSDCard`. Actual successful transactions update B-Coin income/spending (developer funds excluded). `PlayerAnalytics.Complete` records the final grades inside its existing exactly-once completion guard. Previewing or reopening feedback does not award progress.
- Counts include saved takes/duration, graded attempts, passed/failed attempts, five distinct completed clients, best/average overall score, best letter grade, income/spending, per-client best scores and the latest five submissions. Best numeric score and passing status are separate: an F with 99/100 remains failed. Lifetime totals do not shrink when the analytics history trims to its 50-result limit.
- Ordinary contract/budget retries retain lifetime stats and achievement keys while restoring contract budget/purchases. A new career starts empty; the F12 panel's confirmed career-reset button resets only its selected career. `LegacyGameSave` imports/resets the profile key and achievement keys for direct Editor testing too.
- Room preference writes remain separate from the solo career and are never uploaded as its budget. The account view combines observed solo achievement progress; it does not introduce persistent multiplayer achievements, extra unlock notifications or paid rewards.

The radar chart replaces the artwork's static example values. Director uses the retained submissions' average pre-production score, Camera normalizes its /70 grade to /100, Lights normalizes /30 to /100, and Editor uses post-production. Sound is explicitly ungraded and displays a dash rather than a fabricated score. The chart averages the latest retained account analytics (up to 50 submissions); account lifetime totals combine the fixed-size independent career records. Empty or older saves do not invent missing grades. Same-day legacy attempts remain distinct even if they lack submission IDs.

## Achievements

16 built-in achievements cover saved recordings (1, 10, 25), first successful commercial, each of the five clients, all five clients, S grade, post-production ≥95, all three departments ≥90, a pass after a failed attempt at the same brief, an unassisted fully tracked first-attempt pass, and a fully tracked unassisted pass retaining ≥1,000 B-Coins without rejected purchases or untracked balance changes. Quality milestones require a passing final letter grade, including mandatory contract requirements.

Progress mirrors the existing `AchivProg_career_*` / `AchivDone_career_*` keys. Each achievement unlocks once, with a non-blocking notification; it does not grant B-Coins, C-Coins or cosmetic items. Existing custom serialized achievements and `AddAchievementProgress` remain supported; arbitrary increments cannot unlock the built-in gameplay achievements.

## Older saves

First access imports completion flags, stored per-client best scores and retained analytics results. It does not invent missing attempts, grades or recording durations. The Stats tab explains partial totals; a `+` after recorded duration means earlier take durations were not saved. First-attempt awards are withheld for clients whose earlier attempts may be missing, but new fully tracked clients can still earn them. Legacy unlocks are restored silently.
