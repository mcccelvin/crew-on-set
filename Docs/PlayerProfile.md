# Player profile, achievements and statistics

The main-menu Account screen and the in-game Profile HUD button (**I**) open the same profile view. It uses the original curtain/stage backdrop, girl character preview, paper panels, title signs and three icon tabs: **Profile**, **Stats** and **Shop**. Achievements open from the Stats footer and return to Stats without closing the profile. Back/Close return to the originating menu or gameplay using the existing input-state handling. All pages share the screen-scaling canvas (1920×1080 reference, Expand). Stats and achievements use bundled Kalam/Allura pen fonts, opaque paper cards and visible scrollbars. The live portrait uses the bundled stage idle and a periodic greeting, corrects imported rig/skin scaling, and uses scale-independent lighting so the mesh is neither clipped nor a black silhouette.

## Shared account details and shop

Profile text uses bold white sans-serif lettering with a black outline, matching the authored NAME label style. A profile-only shared material styles account fields, controls, Stats, achievements and cosmetic-shop text when built/refreshed. Feedback-report typography is unchanged.

The profile uses `ProfileCharacterPreview` instead of a frozen portrait: the original rig idles for one second after opening, plays the authored `Assets/Player/Animations/Waving Gesture.fbx`, then rests for five seconds after the full clip ends before repeating. `Resources/ProfileWave.controller` references the original humanoid clip and includes it in builds; no procedural arm rotations are applied. The preview sits on the authored platform and uses unscaled time while gameplay is paused. A playable mixer eases between idle and the gesture. Manual animation evaluation and reusable baked display meshes keep the final greeting pose visible in the portrait camera; rendering is capped at 30 updates/second. Closing/replacing the portrait releases its graph, meshes and isolated rig. TRY ON still uses the same fitted clothing and never grants ownership. The top-left C-Coin counter uses a gold C emblem, translucent gray balance bar and white numerals inspired by the B-Coin HUD; cached/pending status remains separate from the spendable balance.

Name and Bio are editable on the Profile paper; SAVE preserves them and the account ID remains read-only. `AccountProfileData` caches identity in global, per-account `SaveSystem.Profile.v1.<accountId>` preferences, separate from career checkpoints and budget retries. Authenticated saves update the existing PlayFab title display name and private `ProfileBio` user data. Guest/offline edits remain local with an explicit pending status; a late reply from an old account or an earlier read cannot overwrite a newly saved edit. Account switching discards the previous account's draft. No live backend deployment or payment changes are introduced here.

`AccountProfileMenuHost` intercepts the existing Account scene/main-menu Account Profile entry, disabling its old display canvas while the shared view is open. It does not require changing existing menu button events. The career badge and SWITCH CAREER control are removed. Main-menu and in-game Stats use the same read-only projection of the current account's saved productions, including unsaved progress from its active career. Opening the profile does not select another career, change gameplay preferences or award currency.

**SYNC ACCOUNT** saves the active solo checkpoint, downloads/merges account-owned checkpoints and uploads pending revisions through the existing private PlayFab transport. The payload already carries career stats/achievements, analytics and `PlayerMoney`; no separate or fabricated stat values are uploaded. Name/Bio refresh and C-Coin wallet refresh are separate requests. Successful checkpoint status explicitly says **Stats and B-Coin budgets synced with PlayFab**; it does not claim that C-Coins have synced. Guest/offline data remains local. The button is disabled while progress or wallet sync is busy; late callbacks are checked against both the current repository/session and the authenticated SDK player ID.

B-Coins remain independent commercial budgets: the Stats page shows the current production's B-Coins, or the latest saved budget when no career is active, never a sum of spendable budgets. The game reads C-Coins and cosmetic inventory directly from the signed-in PlayFab account, matching the website's live PlayFab wallet/catalog. This sync requires the website to run in real mode with the same PlayFab title and `CC` currency; mock/demo balances remain local samples. `Tools/CloudScript/CrewCCoins.js` is a bounded interim reward handler that still needs to be deployed in PlayFab; it limits claims to one per level/account but cannot prove local level completion.

The Shop paper has Accessories, Hair, Face, Body, Tops, Bottoms, Shoe Wear and Frames tabs. Website-matched cosmetics use the website PlayFab item IDs, labels, names and C-Coin prices; the five free face looks are automatically owned. The original customization folder still supplies the model thumbnails and unsaved TRY ON previews. PlayFab owns the shared account balance and purchased item inventory. BODY has no website catalog entry. Owned parts can be equipped one per category, independently of the frame. DEFAULT LOOK removes selections without deleting ownership. TRY ON dresses the original `DefaultCharacGirlRig`: only the selected slot is replaced, while other clothes, hair, face and accessories remain. Successive trials can be combined; another item in the same slot replaces the previous trial. Leaving the Shop, closing/reopening the profile or a wallet refresh restores confirmed equipped items. Trials do not change ownership, wallet balance or saved equipment.

`CharacterCosmeticRig.asset` contains generated skin weights and original material references for all 36 models. `CharacterCosmeticRigBaker` transfers the base body's weights in shared authored space and retains its original bind matrices, then the existing profile renderer samples the bundled idle. Hair and facial parts follow the head. Original FBXs and their import settings are unchanged. Rebuild this derived asset with **Crew-On-Set > Cosmetics > Rebuild profile clothing rig** outside Play mode after changing the models. This is a profile portrait fitting system, not gameplay/multiplayer equipment replication; new body shapes or extreme clothing may require artist-authored fit/weights. See `Docs/CCoins.md` for the catalog manifest and undeployed backend/payment requirements.

`ProfileSkillsChart` derives from `MaskableGraphic`, so the existing Stats viewport clips its polygon and grid while scrolling. It cannot draw over the heading, account subtitle or curtain background.

## Ownership and persistence

- `AlmanacProfile.cs` owns the original profile/portrait. `AlmanacProfileProgress.cs` upgrades existing authored profiles without duplicating panels, binds the Stats tab, refreshes stats and achievement cards, and preserves the existing serialized/public profile entry points. `AlmanacProfileAccount.cs` shares account inputs, progress-sync action and the shop paper between both entry points; `ProfileSkillsChart` draws the live native UI radar chart.
- `CareerProfileProgress.cs` stores fixed-size lifetime statistics in career-scoped `Profile.Career.v1` through `GameSavePrefs`. It never caches a different account/career's record. Existing checkpoint/cloud transport carries this value with the selected save; no new wallet or payment APIs are used.
- `AccountProductionProfile` reads only saves belonging to the current owner. It combines lifetime counters from independent productions, unions completed clients/observed milestones and retains graded analytics for the chart. It never activates a save. Checkpoint copies share `Profile.CareerOrigin.v1`; overlapping histories are not summed. A differing offline fork uses one whole stored lifetime record (longer tracked history first), preserves observed milestones and discloses conservative totals. Older copies use the existing reward-origin ID when available, otherwise their save ID. Deleted checkpoints can retain earned statistics but do not supply a usable budget. Completely reset or missing records are not reconstructed from invented results.
- `PlayerAnalytics.Begin` initializes tracking before a new attempt. Actual saved camera takes pass duration from `FilmCameraItem.EjectUsedSDCard`. Actual successful transactions update B-Coin income/spending (developer funds excluded). `PlayerAnalytics.Complete` records the final grades inside its existing exactly-once completion guard. Previewing or reopening feedback does not award progress.
- Counts include saved takes/duration, graded attempts, passed/failed attempts, five distinct completed clients, best/average overall score, best letter grade, income/spending, per-client best scores and the latest five submissions. Best numeric score and passing status are separate: an F with 99/100 remains failed. Lifetime totals do not shrink when the analytics history trims to its 50-result limit.
- Ordinary contract/budget retries retain lifetime stats and achievement keys while restoring contract budget/purchases. A new career starts empty; the F12 panel's confirmed career-reset button resets only its selected career. `LegacyGameSave` imports/resets the profile key and achievement keys for direct Editor testing too.
- Room preference writes remain separate from the solo career and are never uploaded as its budget. The account view combines observed solo achievement progress; it does not introduce persistent multiplayer achievements, extra unlock notifications or paid rewards.

The radar chart replaces the artwork's static example values. Director uses the retained submissions' average pre-production score, Camera normalizes its /70 grade to /100, Lights normalizes /30 to /100, and Editor uses post-production. Sound is explicitly ungraded and displays a dash rather than a fabricated score. The chart averages the latest retained account analytics (up to 50 submissions); account lifetime totals combine the fixed-size independent career records. Empty or older saves do not invent missing grades. Same-day legacy attempts remain distinct even if they lack submission IDs.

## Achievements

16 built-in achievements cover saved recordings (1, 10, 25), first successful commercial, each of the five clients, all five clients, S grade, post-production ≥95, all three departments ≥90, a pass after a failed attempt at the same brief, an unassisted fully tracked first-attempt pass, and a fully tracked unassisted pass retaining ≥1,000 B-Coins without rejected purchases or untracked balance changes. Quality milestones require a passing final letter grade, including mandatory contract requirements.

Progress mirrors the existing `AchivProg_career_*` / `AchivDone_career_*` keys. Each achievement unlocks once, with a non-blocking notification; it does not grant B-Coins, C-Coins or cosmetic items. Existing custom serialized achievements and `AddAchievementProgress` remain supported; arbitrary increments cannot unlock the built-in gameplay achievements.

## Older saves

First access imports completion flags, stored per-client best scores and retained analytics results. It does not invent missing attempts, grades or recording durations. The Stats tab explains partial totals; a `+` after recorded duration means earlier take durations were not saved. First-attempt awards are withheld for clients whose earlier attempts may be missing, but new fully tracked clients can still earn them. Legacy unlocks are restored silently.

## Verification

Compile against actual Unity Editor and actual standalone-player references. In an isolated Unity project, exercise progress/analytics/preferences/profile partials and real checkpoint repository using native JsonUtility, UI, TMP and bundled fonts. Test failed-high-score gates, repeated completion, retries, independent saves, reload/reset, room isolation, legacy/corrupt data, money/assistance gates, lifetime counters beyond 50 results, account-specific identity, pending edits and stale callbacks. Test account projection, checkpoint lineage/conflicts and unchanged extracted sync methods against a simulated PlayFab transport: private actual stats/budget payloads, download before upload, failure/retry, stale-account callbacks and second-device restoration. Check both profile entry points and SYNC ACCOUNT. Render Profile/Stats/Achievements/Shop at 1920×1080, 1280×1024 and 2560×1080, inspect text visibility and reuse of authored UI. Unrelated scene, wallet and PlayFab services are fixtures; this is not a full game build or a live PlayFab sync test.

Include the original script `.meta` files in the isolated project and validate their GUIDs as exactly 32 hexadecimal characters before compiling. A source-only compiler check cannot detect Unity skipping a script because its asset metadata is invalid.
